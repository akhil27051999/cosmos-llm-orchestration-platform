Async & the Event Loop

how one worker serves thousands

1The core idea

Your app spends most of its life waiting — for the database, the internet, the AI. Async is the trick of doing other useful work during those waits, using just one worker.

🍽️ Analogy — one waiter, many tables A restaurant with one waiter. The slow way: take Table 1's order, then stand in the kitchen until it's cooked before touching Table 2. The smart way: hand Table 1's order to the kitchen and immediately serve Table 2 while it cooks; deliver when the bell rings. One waiter, many tables — because the cooking (waiting) is the slow part, not the waiter.

Waiter = one thread · Tables = requests · Kitchen cooking = I/O wait · “serve another table while it cooks” = await.

2Sync vs Async — see the difference

💡 Key insightAsync doesn't make one task faster — it stops the worker from sitting idle, so many tasks finish in the same wall-clock time.

3What is the “event loop”?

The event loop is the waiter's brain: a while True: that runs forever asking one question — “who's ready for their next step?” — and running whoever is ready.

4What happens at await?

await means: “this might take a while — pause me, go help others, wake me when my result is ready.”

💡 The subtle part (bites people later)Between two awaits your code runs uninterrupted — nobody touches your variables. But across an await, the world can change (other tasks ran while you were paused). This is the seed of the “async race conditions” we'll handle in later stages.

5The #1 sin: blocking the loop

Because there's one worker, if a task refuses to await and does something slow synchronously, the whole app freezes.

🚫 The ruleIn async code, never call a blocking function. Use the async version:
time.sleep() ❌ → await asyncio.sleep() ✅  ·  requests.get() ❌ → await httpx.get() ✅  ·  sync DB driver ❌ → async driver ✅  ·  heavy CPU work → push to a separate worker pool.
🍽️ AnalogyBlocking = the waiter walks into the kitchen and personally cooks one dish while every other table sits ignored.

6Async is NOT parallelism

Everything above happens on one worker, one CPU core. Async overlaps waiting, not computing.

🛠️ Your DevOps bridgeThis is exactly how nginx / Envoy serve tens of thousands of connections on a few threads with an epoll/kqueue event loop. And “blocking the loop” is the same “one bad call wedged the whole pod” incident you've debugged — now you know the mechanism.
📝 Cheat-sheet — the whole lesson in 8 lines
  • App spends most time waiting → async fills those waits with other work.
  • 1 thread + event loop = one waiter serving many tables.
  • await = “pause me, help others, wake me when ready.”
  • Between awaits: uninterrupted. Across an await: the world may have changed.
  • A blocking call on the loop = the whole app freezes (cardinal sin).
  • Fix: always use async versions (asyncio.sleep, httpx, async DB driver).
  • async = concurrency (overlap waits), NOT parallelism (overlap CPU).
  • I/O-bound → async.   CPU-bound → processes.

Types & Pydantic

labels for data + a guard at the door

1How a Python variable really works

A variable name is just a sticky tag you put on a box (an object). The type lives on the box, not the tag — and you can peel the tag off and stick it on a different box anytime.

This is dynamic typing. Breezy for scripts, but risky at scale: a wrong-type value rides silently through five functions and explodes far away. Application Python tames this with types.

2Type hints are labels — ignored at runtime

You label functions: def add(a: int, b: int) -> int. But the Python interpreter does not enforce them — add("x","y") still runs.

📦 AnalogyA type hint is like writing “FRAGILE — GLASS” on a box. The label doesn't physically stop someone packing a brick — it's guidance for humans and tools. Two “guards” read those labels for you 👇

3Guard #1 — mypy (the inspector, before the flight)

mypy reads your labels and checks your code before it runs: add("x", 1) → ✗ expected int, got str.

🛫 Analogymypy = the airport inspector who X-rays every labeled box at check-in — catching “you said glass but packed a brick” before the plane departs, not at 30,000 ft (3am in prod). Put it in CI and a whole class of bugs dies at dev time.
🔤 The typing words you'll use list[int], dict[str, float] · str | None (optional) · Literal["pending","running","done"] (only these exact values) · Protocol (“anything with these methods fits” — for ports/adapters).

4Guard #2 — Pydantic (customs, at the border)

Hints don't check incoming data. When a client sends {"priority":"abc"}, plain Python won't stop it landing in an int field. At a trust boundary (API request, config, third-party data) you need runtime checking — that's Pydantic v2: it parses, validates, and coerces, and rejects bad input loudly.

🛃 AnalogyPydantic = the customs officer at the border — opens each incoming bag, checks it matches the declared contents, converts where sensible, and loudly rejects what's wrong. (v2's core is Rust → fast; FastAPI uses it automatically → clean 422 for free.)

5The pattern: validate at the edges, trust the inside

🛂 AnalogyAirport security screens you once at the entrance; inside the secure zone you're trusted — nobody re-screens at every gate. Pydantic at the doors, plain typed objects inside.
🛠️ Your DevOps bridgeThis is JSON Schema / OpenAPI request validation / Terraform variable type constraints — the same idea, now living inside your Python at its boundary.
📝 Cheat-sheet
  • A variable is a tag; the type lives on the object, not the name (dynamic typing).
  • Type hints are labels — the interpreter ignores them at runtime.
  • mypy = static inspector: catches type bugs before you run (put it in CI).
  • Pydantic = runtime customs at the boundary: parse, coerce, reject bad input.
  • Use both: mypy for your code, Pydantic for untrusted input.
  • Pattern: validate at the edges, trust the typed core.
  • Handy types: list[int], str | None, Literal[...], Protocol.
  • FastAPI uses Pydantic automatically → clean 422 on bad requests.

Generators & Coroutines

the machinery under async

1The idea: a function that can pause

Normal functions run start-to-finish and forget everything. A generator can pause in the middle, hand back a value, and later resume exactly where it left off — remembering all its variables.

🍬 Analogy — a Pez dispenserA normal function dumps the whole bag of candy at once. A generator is a Pez dispenser: press once → one candy (yield), it pauses; press again → the next one. It produces values one at a time, on demand (lazily), so it never has to hold the whole bag in memory.

2Coroutines = the same trick, for async

An async def function is a coroutine — it uses the exact same “pause & resume” machinery as a generator. The only difference: a generator pauses at yield to hand back data; a coroutine pauses at await to hand back control to the event loop (Lesson 1!).

💡 Key insightCalling async def f() does nothing by itself — it just creates a coroutine object sitting there, inert. It only runs when the event loop awaits/schedules it. (Like a recipe card: writing it doesn't cook anything; a chef has to pick it up.)
🔗 Ties back to L1“await pauses my task and lets others run” works because coroutines are pausable functions. Now you know the gears inside the event loop.
📝 Cheat-sheet
  • Generator = a function that pauses at yield, produces values lazily (one at a time).
  • It remembers its place & variables between resumes.
  • Coroutine (async def) = same pause/resume machinery, pauses at await.
  • yield hands back data; await hands back control.
  • Calling a coroutine returns an inert object — it runs only when awaited/scheduled.
  • Generators save memory (lazy); great for streaming large data.

Context Managers

borrow → use → always return

1The problem: things you must clean up

Files, database sessions, network connections, locks — you open/acquire them, use them, and must release them. If an error happens mid-use and you forget to release, you leak resources (connections pile up, the app dies).

📚 Analogy — a library bookA context manager (with) is like borrowing a library book that returns itself automatically the moment you leave — even if you trip and fall on the way out (an exception). You literally cannot forget to return it.

2async with for async resources

Async resources (a DB session, an HTTP client) use async with (backed by __aenter__/__aexit__). You'll use this constantly in Stage 0.5 for the SQLAlchemy session — open a session, do work, and it commits/closes safely even on error.

💡 Two ways to make oneA class with __enter__/__exit__, or the easy way: decorate a generator with @contextlib.contextmanager — the code before yield is “acquire,” after is “release.” (Notice: generators show up again!)
📝 Cheat-sheet
  • with guarantees cleanup runs — even if an exception is thrown.
  • Mechanism: __enter__ (acquire) → body → __exit__ (release, always).
  • async with = the async version (__aenter__/__aexit__) for DB sessions, connections.
  • Build one via a class, or @contextmanager on a generator.
  • Use for: files, DB sessions, locks, connections — anything you must release.

Decorators

wrap a function to add behavior

1The idea: gift-wrapping a function

In Python, functions are just objects you can pass around. A decorator takes a function, wraps it in an extra layer that runs code before/after, and returns the wrapped version — without changing the original function's code.

🎁 Analogy — gift wrappingThe gift inside is unchanged; you add a layer around it. Decorators add cross-cutting behavior — logging, timing, auth checks, retries, caching — the same way, to many functions, without copy-pasting that logic into each.

2You'll see these everywhere

@app.get("/jobs") (FastAPI routes), @pytest.fixture (tests), @property, @lru_cache — all decorators. Tip: use functools.wraps inside your decorator so the wrapped function keeps its real name and docs (otherwise debugging gets confusing).

🛠️ Your DevOps bridgeA decorator is basically middleware for a single function — the same “run something before/after” idea as nginx/Envoy filters or HTTP middleware, at function scope.
📝 Cheat-sheet
  • Functions are objects → you can wrap them.
  • A decorator takes a function, returns a wrapped one that adds before/after behavior.
  • @name above a function applies the decorator.
  • Great for cross-cutting concerns: logging, timing, auth, retry, caching.
  • Use functools.wraps to preserve the original name/docs.
  • FastAPI & pytest are built on decorators.

Dataclasses vs Pydantic

two kinds of “data box”

1Two containers for structured data

Both hold structured data with named, typed fields. The difference is whether they validate:

📦 AnalogyA dataclass is a labeled box you pack yourself (you trust the contents). A Pydantic model is a box with a customs inspector who checks everything going in. Don't pay for the inspector on internal boxes you already trust.
💡 Rule of thumbUntrusted input crosses a boundary → Pydantic. Internal, already-validated domain object → dataclass. (This is the “validate at the edges, trust the core” pattern from L2, made concrete.)
📝 Cheat-sheet
  • Both = typed, named-field containers.
  • @dataclass: no validation, fast, for trusted internal data; frozen=True = immutable.
  • Pydantic: validates + coerces + (de)serializes; for untrusted boundary data.
  • Pick by where the data comes from: edge → Pydantic, core → dataclass.

Testing — pytest & Hypothesis

your safety net

1Why tests (the real reason)

Tests aren't about proving code works today — they're a safety net that lets you change code tomorrow without fear. For a long-lived platform, that confidence is everything.

🧯 AnalogyTests are smoke alarms throughout the house. You don't notice them daily, but the moment you break something, one goes off — right next to the problem, not after the house burns down in production.

2The pytest toolkit

3Hypothesis — the robot that breaks your code

Normal tests check examples you think of. Property-based testing (Hypothesis) flips it: you state a property that must always hold (“encoding then decoding returns the original”), and Hypothesis throws hundreds of weird inputs at it to find a counterexample — then shrinks it to the smallest failing case.

💡 Why it's powerfulIt finds the edge cases you'd never think to write — empty strings, huge numbers, unicode, zero. Great for parsers, encoders, and pure logic.
📝 Cheat-sheet
  • Tests = a safety net for fearless change, not busywork.
  • fixtures = setup/teardown & dependency injection for tests.
  • parametrize = same test, many inputs.
  • mocking = fake the slow/external stuff (DB, APIs).
  • pytest-asyncio = test async code.
  • Hypothesis = state a property; it hunts counterexamples.
  • Test pyramid: many fast unit tests, fewer integration, fewest end-to-end.

Async SQLAlchemy 2.0

talking to Postgres without blocking

1The three pieces

🛒 AnalogyThe session is a shopping cart: you toss items in as you shop, and nothing is actually bought until checkout (commit). If you change your mind, empty the cart (rollback) — the store shelves (DB) are untouched.

2Why async here matters

Use the async driver (asyncpg) with AsyncSession and async with. Reason: a DB query is I/O — with a sync driver it would block the event loop (Lesson 1's cardinal sin!) and freeze every other request. The async driver lets the loop serve others while the DB works.

🔗 Ties to Stage 0You'll hide the session behind a repository (e.g., JobRepository.get(id)) so your business logic never touches SQL directly — that's the “ports & adapters” idea you'll formalize in Stage 0.
⚠️ Watch outThe N+1 query problem: looping over 100 jobs and lazily loading each one's rows = 101 queries. Load them together (eager loading) instead. Classic performance trap.
📝 Cheat-sheet
  • Engine = connection pool (reused DB connections).
  • Session = unit of work / shopping cart; commit = checkout, rollback = undo.
  • ORM = maps Python objects ↔ SQL rows.
  • Use the async driver (asyncpg) + async with so DB calls don't block the loop.
  • Hide it behind a repository (keeps SQL out of business logic).
  • Beware the N+1 query trap — load related rows together.

Alembic Migrations

version control for your database

1The problem: the schema must change over time

You'll add columns, tables, indexes as the app grows. But the database already has real data — you can't just drop and recreate it. You need ordered, repeatable, reversible changes that every environment (your laptop, staging, prod) applies identically.

🗂️ Analogy — git for your schemaAlembic is version control for the database structure. Each migration is like a commit: a numbered step with an upgrade() (go forward) and downgrade() (roll back). The chain of migrations = the schema's history.

2Autogenerate — with a warning

Alembic can compare your ORM models to the actual DB and auto-write a candidate migration. Huge time-saver — but always read what it generated before applying (it can miss renames or generate destructive steps). Golden rule: never edit a migration that has already shipped — add a new one.

📝 Cheat-sheet
  • Migration = a versioned, ordered, reversible schema change (like a git commit).
  • upgrade() = apply; downgrade() = revert.
  • Autogenerate diffs models vs DB → candidate migration (always review it!).
  • Run migrations in deploy/CI so every environment matches.
  • Never edit an already-shipped migration — write a new one.

Project Hygiene — uv, venv, pyproject

reproducible, isolated projects

1Virtual environments — isolation

A virtual environment is a private, isolated set of installed packages per project, so Project A's libraries never clash with Project B's (or your system Python).

🧰 AnalogyA venv is a clean, dedicated workshop for one project — its own tools on the bench. You don't share one messy garage across every project and hope nothing conflicts.

2uv, lockfiles & pyproject.toml

uv is a fast, modern tool that creates the venv, installs dependencies, and (crucially) writes a lockfile — the exact pinned versions of every package. That makes installs reproducible: your machine, a teammate's, and CI all build the identical environment. pyproject.toml is the project's spec sheet (name, deps, dev-deps, tooling config).

💡 Why the lockfile matters“Works on my machine” bugs usually mean different package versions. A lockfile makes the environment exact and repeatable everywhere — the same reproducibility instinct you already have from Docker images and Terraform.
📝 Cheat-sheet
  • venv = isolated packages per project (no cross-project clashes).
  • uv = fast tool for venv + install + lockfile (modern pip/venv replacement).
  • Lockfile = exact pinned versions → reproducible installs everywhere.
  • pyproject.toml = project metadata, dependencies, tool config.
  • Separate runtime deps from dev deps (pytest, mypy).

Hexagonal architecture (ports & adapters)

keep the core pure

1The idea: a pure core, swappable edges

Put your business logic in the center (the domain). It never imports FastAPI or SQLAlchemy. It talks to the outside world only through ports (interfaces). The outside world (web, DB) plugs in as adapters that implement those ports.

🔌 Analogy — a power socketYour appliance (the domain) doesn't care if the electricity comes from solar or the grid — it just plugs into the socket (port). You can swap the power source (Postgres → a fake DB for tests) without rewiring the appliance.

💡 The one ruleArrows only point inward. The core defines an interface like JobRepository; the SQLAlchemy adapter implements it. The core never knows SQLAlchemy exists.

2Why bother

Testability (swap the DB for an in-memory fake → fast unit tests). Framework independence (change web framework or DB without touching rules). Clarity (business logic isn't tangled with I/O).

📝 Cheat-sheet
  • Domain core = pure business logic; imports no framework.
  • Port = an interface the core defines (e.g. JobRepository).
  • Adapter = an implementation of a port (FastAPI, SQLAlchemy).
  • Dependencies point inward; outer layers depend on inner, never the reverse.
  • Payoff: swap DB/framework & test the core in isolation.

Idempotency keys

safe retries

1The problem: everything retries

A client sends POST /jobs, the network hiccups, the client retries — now you might create two jobs. An idempotency key (a unique id the client sends) makes the repeat safe: same key → same single result.

🎟️ Analogy — a concert ticketScanning your ticket twice still gets you one seat, not two. Or an elevator button: pressing it 5 times doesn't summon 5 elevators.

🔗 Why it's foundationalOnce you add a queue (L/Stage 1), retries are everywhere. Idempotency is the seatbelt that makes “at-least-once” delivery safe.
📝 Cheat-sheet
  • Client sends a unique key per logical request.
  • Store key → result; a repeat returns the stored result (no duplicate).
  • Turns unsafe retries into safe ones.
  • Essential companion to at-least-once delivery & queues.

Optimistic concurrency control (OCC)

no lost updates, no locks

1The lost-update problem

Two requests read the same job (version 3), both change it, both save — the second silently overwrites the first. OCC prevents this with a version number: you save only if the version is still what you read; otherwise you re-read and retry.

📝 Analogy — Google Docs / WikipediaIf someone saved an edit between your read and your write, you get “this changed — reload.” You don't silently clobber their work; you re-base on the latest and try again.

💡 Optimistic vs pessimisticOptimistic = assume conflicts are rare, detect & retry (no locks, high concurrency). Pessimistic = lock the row first (safe but serializes writers, risks deadlocks). OCC fits web apps where conflicts are rare.
📝 Cheat-sheet
  • Add a version column; bump it on every write.
  • Update “WHERE id=? AND version=?”; 0 rows updated = conflict → retry.
  • Prevents the “lost update” bug without locking.
  • Optimistic (detect+retry) vs pessimistic (lock first).

Accept vs Process (202 + id)

respond fast, work later

1The problem: slow work must not block the request

An agent job runs for seconds to minutes. If the HTTP handler waited for it, every in-flight job would hold a connection open — and a burst of traffic would exhaust your connection pool and the server would stop accepting anything. You have to answer the client in milliseconds regardless of how long the work takes.

2The handshake: 202 + a job id

So you split accepting from processing. The gateway validates the request, writes a job row, immediately returns 202 Accepted + a job id, and drops the job onto a queue. The heavy lifting happens later in a background worker. The id is the client's claim ticket.

3How the client gets the result

With just an id, the client either polls GET /jobs/{id} until it's done, or streams live updates over SSE. Either way the request that submitted the work returned instantly — the system stays responsive no matter how slow the job is.

🧺 Analogy — the dry-cleanerThey take your clothes and hand you a numbered ticket instantly — they don't clean them at the counter while you stand there. You return (or get a text) when it's ready.
💡 The id is a contractThat job id is how the client tracks, polls, streams, and cancels the work later. It's also what makes the request safely retryable when combined with idempotency.
🔗 Ties to S0·3A retried submit must not create two jobs — so the 202 handshake pairs with the idempotency key from Stage 0. Same key → same job, even if the client sends it twice.

Durable Queue

work that survives a crash

1A buffer between fast producers and slow consumers

The gateway produces jobs quickly; workers consume them slowly. A durable queue sits between them, absorbing the mismatch. Producers never wait on consumers, and consumers pull at their own pace.

2Durability & acknowledgement

“Durable” means a job isn't lost if a worker crashes. The worker acknowledges (acks) a message only after it finishes processing. If it dies mid-job before acking, the queue redelivers the message to another worker — nothing is dropped (this is why at-least-once + idempotency, 1·5, matter).

3Load leveling — spikes become queue depth

A traffic spike doesn't overwhelm the workers; it just makes the queue longer. Workers drain it steadily. This “queue-based load leveling” is what keeps the system stable under bursts — the queue is a shock absorber.

🏭 Analogy — a conveyor beltOrders drop onto a belt; cooks take the next when free. If a cook steps away (worker restarts), the orders stay on the belt. A rush just makes the belt longer.
💡 Ack timing is a design choiceAck after success = at-least-once (safe, may duplicate). Ack before = at-most-once (may lose work). For jobs you almost always want ack-after + idempotent processing.
🔗 Redis Streams now, Kafka laterYou start with Redis Streams for simplicity; Stage 5 swaps in Kafka when you need partitioned scale, replay, and multiple independent consumers.
📝 Cheat-sheet
  • Queue = persistent buffer decoupling producers from consumers.
  • Ack after processing → redelivery on crash (nothing lost).
  • Load leveling: spikes become queue depth, not overload.
  • Ack-after = at-least-once; ack-before = at-most-once.
  • Redis Streams to start; Kafka in Stage 5.

Job State Machine

only legal transitions

1Define the states — and forbid the impossible ones

A job lives in one of a fixed set of states, and can only move along defined transitions. Making the states and moves explicit means illegal states simply can't happen — the code won't let a job jump from pending straight to done.

2Guards reject illegal moves

Every transition is guarded: attempting an undefined move (e.g. done → running) must raise, not silently corrupt state. The state machine is a hard guardrail that turns “update the status field” into “make a valid transition.”

3Each transition is an event

Crucially, every legal transition emits an event (JobStarted, JobSucceeded…). That's the bridge to event sourcing (1·4): the state machine decides what's allowed; the event log records what happened. Terminal states (done/failed/cancelled) are final — no transitions out.

📦 Analogy — parcel tracking“accepted → in transit → delivered.” A parcel can't teleport to “delivered” without “in transit.” The tracking page only ever shows a real, ordered stage.
⚠️ Don't just set a status columnA bare status field lets any code write any value, from anywhere — the source of “how did this job end up running and done?” bugs. The state machine centralizes and validates every change.
🔗 Feeds the event logEach valid transition produces the event that 1·4 stores. State machine = rules; event log = history.
📝 Cheat-sheet
  • Fixed states; only defined transitions allowed.
  • Guard & reject illegal transitions (raise).
  • Every transition emits an event.
  • Terminal states (done/failed/cancelled) are final.
  • Centralizes state changes — no scattered status writes.

Event Sourcing

store the story, derive the state

1Store every change, not just the latest value

Instead of overwriting a job's status, you append every change as an immutable event (JobCreated, JobStarted, JobSucceeded…). The event log is the source of truth; the “current status” is something you compute, not something you store.

2Deriving state by folding the log

To know a job's current state, you replay its events from the start, applying each to build up the state — a “fold.” Because you kept every step, you can reconstruct the state at any point in time, not just now.

3The superpowers — and the cost

You get a perfect audit trail (“what happened to job X and when?” is always answerable), time-travel debugging, and the ability to build brand-new read-models by replaying (this is the seed of CQRS in Stage 5). The cost: you derive state instead of reading it, so hot paths use periodic snapshots to avoid replaying millions of events.

🏦 Analogy — a bank statementYour bank stores every transaction, not just a balance. You can always see how you reached today's balance, audit any moment, and never lose history.
💡 Snapshots keep it fastReplaying the whole log every read is slow. Periodically save a snapshot of derived state, then replay only the events since the snapshot.
🔗 Sets up CQRS (Stage 5)Because state is derived from events, you can project those same events into multiple read-optimized views — exactly what CQRS does.
📝 Cheat-sheet
  • Append-only event log is the source of truth.
  • Current state = fold/replay over events.
  • Full audit trail + time-travel + rebuildable read-models.
  • Use snapshots so hot reads don't replay everything.
  • Trade-off: more moving parts than a status column.

At-least-once & Idempotent Consumers

the exactly-once myth

1Why the same message gets delivered twice

Queues guarantee at-least-once delivery. The classic case: a worker processes a job successfully, then crashes before it can ack. The queue, never told it succeeded, redelivers the message — so the work runs a second time. Duplicates are not a bug to avoid; they're a reality to design for.

2Idempotent processing makes duplicates harmless

An idempotent consumer keys its work by a stable id (event id / sequence). Before acting, it asks “have I already handled this id?” If yes, it's a no-op; if no, it processes once and records the id. Now delivering twice changes nothing.

3The “exactly-once” myth

Exactly-once delivery is impossible across an unreliable network — you can't both guarantee delivery and guarantee no duplicates. What you achieve is effectively-once = at-least-once delivery + idempotent processing. Saying this precisely is a senior signal.

🔔 Analogy — a duplicate reminderYour phone shows the same reminder twice. If the action is “mark done,” seeing it twice is harmless. If it were “charge the card,” duplication is a disaster — so you design it to be safe.
⚠️ Ack only after successIf you ack before processing, a crash loses the work (at-most-once). Ack after, and make processing idempotent — that's the safe combination for jobs.
🔗 Same thread as S0·3Idempotency keys (submit) and idempotent consumers (process) are the same principle at two layers: retries are everywhere, so make repeats harmless.
📝 Cheat-sheet
  • Queues deliver at-least-once → expect duplicates.
  • Idempotent consumer: key by id; reprocessing is a no-op.
  • Ack only after successful processing.
  • “Exactly-once delivery” is a myth → aim for effectively-once.
  • Effectively-once = at-least-once + idempotency.

Cancellation

stopping work in flight

1Why long jobs must be stoppable

Agent jobs can run for minutes and cost real money. Users change their minds; runaway jobs must be stoppable. But you can't just kill a worker mid-operation — that risks half-written state and leaked resources.

2Cooperative cancellation

So cancellation is cooperative: a cancel request appends a JobCancelled signal, and the worker checks for it at safe checkpoints in the loop (e.g. between agent steps). It won't abandon a half-finished operation, but before starting the next step it sees the signal and stops.

3Clean up, then record the ending

On seeing the signal the worker releases resources (open connections, partial writes), then records the terminal cancelled state via the event log — so the job's history clearly ends in cancellation, not a mysterious stall.

🍳 Analogy — a “cancel order” buttonThe kitchen checks the cancel board between steps. It won't abandon a half-cracked egg mid-motion, but before the next step it sees “cancelled,” stops, and clears the station.
💡 Same idea as Go's contextCooperative cancellation via a checked signal is exactly what Go's context does (Stage 7) — pass a cancel signal down and check it at boundaries.
🔗 Uses the state machine + event logCancellation is just another guarded transition ((pending|running) → cancelled) that emits an event — reusing 1·3 and 1·4.
📝 Cheat-sheet
  • Cancellation is cooperative: signal + checkpoint checks.
  • Never hard-kill mid-operation.
  • Clean up partial work before stopping.
  • Record the terminal cancelled state in the log.
  • Same pattern as Go's context cancellation.

Why Polyglot Persistence

the right store per data shape

1No single database is good at everything

Force everything into one database and you get either rigid schemas where you need flexibility, or weak guarantees where you need ACID. Polyglot persistence means deliberately using several stores, each matched to a kind of data.

2Nataraja's data placement

3The cost, and the interview framing

The price of polyglot is a bigger operational surface (more systems to run and back up). The payoff is that each store does one thing excellently. Frame it as: “I put money in Postgres for ACID, trajectories in Mongo for flexibility, counters in Redis for speed.”

Document Modeling — embed vs reference

MongoDB's core decision

1Keep related data together, or link it?

For each relationship in MongoDB you choose: put the related data inside one document (embed), or in a separate document you link to (reference). This single choice drives read speed, duplication, and update cost.

2When to embed

Embed when the data is read together, owned by the parent, and bounded in size. One read returns the whole thing — fast and atomic. Downside: the document grows, and duplicated embedded data is painful to update in many places.

3When to reference (and the limit that forces it)

Reference when the data is large, shared, or unbounded — e.g. an agent trajectory that can grow to thousands of steps. MongoDB caps a document at 16MB, so unbounded lists must be referenced. The guiding question is always: “what do I read together?”

🍱 Analogy — combo meal vs menu numberEmbed = a combo meal on one tray (everything you eat together, one grab). Reference = a menu number you look up separately (good when the item is huge or shared).
⚠️ Beware the giant documentEmbedding an ever-growing list eventually hits the 16MB limit and makes every update rewrite a huge document. Unbounded → reference.
💡 Model for queries, not for tidinessUnlike relational normalization, Mongo modeling optimizes for your access patterns. Shape documents around how you'll read them.
📝 Cheat-sheet
  • Embed: read-together + bounded → one fast read.
  • Reference: large / shared / unbounded data.
  • 16MB document limit forces unbounded lists to reference.
  • Model for query patterns, not normalization dogma.
  • Guiding question: what do I read together?

Aggregation Pipeline

1An assembly line for your data

TTL Indexes

data that expires itself

1Auto-delete transient data

A TTL (time-to-live) index tells MongoDB to automatically delete documents a set time after a timestamp field — no cron job, no cleanup code. The data cleans itself up.

2How it works (and its limits)

A background task sweeps expired documents periodically — so deletion is approximate, not to-the-second. It's ideal for transient data but must not be relied on for exact timing or for data you actually need to keep.

3When to use it — and when not

Great for sessions, caches, one-time tokens, and temp results. Don't use it for anything you must retain, and remember the timing is “soon after expiry,” not precise.

🥛 Analogy — milk with an expiry dateThe carton effectively throws itself out once it's past date. TTL data cleans itself up so you never accumulate stale junk.
💡 Approximate, background timingDocuments disappear soon after expiry, on the sweep — design around “roughly then,” not “exactly then.”
⚠️ Not a durability mechanismTTL silently deletes. Never point it at data you might need later.
📝 Cheat-sheet
  • TTL index auto-expires documents after a set time.
  • Set on a date field; a background task sweeps them.
  • Timing is approximate (near expiry, not exact).
  • Great for sessions/caches/temp data.
  • Never use it for data you must keep.

Redis Caching Patterns

microsecond reads, safely

1Why cache at all

Some reads are expensive (a heavy query, a slow join) but requested often. Redis keeps hot/derived data in memory for microsecond reads, shielding the primary database and cutting latency.

2Cache-aside — the default pattern

The standard approach is cache-aside: check Redis first; on a miss, read the database, then store the result in Redis (with a TTL) for next time. Your code manages the cache alongside the DB.

3The hard part: invalidation

Stale caches cause subtle bugs. Always set a TTL so entries can't live forever, and invalidate or update the cache when the underlying data changes. Watch for the cache stampede: when a hot key expires, many requests miss at once and hammer the DB — mitigate with short locks or staggered TTLs.

🗒️ Analogy — a desk notepadFor answers you look up often, you jot them on a notepad instead of walking to the archive room (the DB) each time. If it's not on the pad, you fetch it once and write it down.
⚠️ Cache invalidation & stampedes“Only two hard things: cache invalidation and naming.” Set TTLs, invalidate on writes, and guard against stampede when a popular key expires.
🔗 Redis does more than cacheThe same Redis also holds rate-limit counters (Stage 4) and hot job state — one fast in-memory store, several jobs.
📝 Cheat-sheet
  • Redis = in-memory, microsecond reads for hot data.
  • Cache-aside: check cache → miss → DB → populate (with TTL).
  • Always set a TTL; invalidate on writes.
  • Beware cache stampede on hot-key expiry.
  • Also used for rate-limit counters & hot state.

The Agent Loop (plan → act → observe)

the heart of the product

1From answering to doing

A single model call answers a question. An agent does a task: it plans a step, acts (calls a tool), observes the result, and loops — accumulating progress until the goal is met.

2How a turn works

Each turn, the model sees the goal + history and returns either a final answer or a tool request. If it's a tool request, you run the tool, append the result to the conversation, and loop. The trajectory (every step) is persisted as you go.

3Terminating safely

An unbounded loop can run forever and burn money, so you bound it three ways: a token budget (3·3), a max-iterations cap, and a no-progress check (stop if it's spinning). Termination logic is as important as the loop itself.

🧑‍💼 Analogy — a junior assistantYou give a goal (“book the cheapest flight”). They think, search, look at results, decide the next step — repeating until done, then reporting back.
⚠️ Always bound the loopToken budget + max iterations + no-progress detection. Without these, one bad task loops forever and runs up the bill.
🔗 Persist the trajectoryEvery step goes to MongoDB (Stage 2, referenced not embedded — it's unbounded) for debugging, evals (3·8), and the live SSE view (3·6).
📝 Cheat-sheet
  • Agent = plan → act (tool) → observe → repeat.
  • Each turn: final answer or a tool request.
  • Terminate on done / token budget / max steps / no progress.
  • Persist every step (the trajectory).
  • Termination logic matters as much as the loop.

Embeddings & Vector Search

finding things by meaning

1Turn meaning into numbers

An embedding converts text into a vector (a list of numbers) that captures its meaning, so texts with similar meaning end up close together in a high-dimensional “meaning space.”

2Searching by nearness

To find relevant text, you embed the query and look for the nearest vectors (top-k). A vector database (pgvector / Qdrant) stores the vectors and does this nearest-neighbor search efficiently, even over millions of items.

3Why it beats keyword search

Keyword search misses “car” when you searched “automobile” — different words, same meaning. Vector search matches on meaning, so it finds semantically related content regardless of exact wording. This is the retrieval engine behind RAG.

🗺️ Analogy — meaning as GPS coordinatesEmbeddings place each text at a location on a map of meaning: “king” and “queen” sit near each other; “banana” is far away. To find relevant text, look for nearby points.

  • Embedding = text → vector capturing meaning.
  • Similar meaning → nearby vectors.
  • Vector search = top-k nearest neighbors (pgvector/Qdrant).

1Look it up, then answer

RAG retrieves relevant documents (via vector search) and injects them into the prompt, so the model answers grounded in your data — not just what it learned in training.

2Why RAG instead of retraining

It adds fresh or private knowledge without retraining the model — you just update the knowledge base. It also lets the model cite sources, and it sharply reduces hallucination on facts that live in your documents.

Rate Limiting

token bucket · sliding window · distributed

1The problem: providers punish bursts

Providers enforce hard limits (e.g. requests/min, tokens/min). Exceed them and you get 429 Too Many Requests — or worse, a temporary ban. With many workers calling in parallel, you must self-regulate the whole fleet's rate, not just each worker's.

2Token bucket — steady rate, controlled burst

Picture a bucket that refills tokens at a fixed rate (say 100/sec) up to a capacity (say 200). Each call must take one token; if the bucket is empty, the call waits or is rejected. The refill rate sets your sustained rate; the capacity sets how big a burst you tolerate after a quiet period.

3Fixed vs sliding window — the boundary spike

A naïve fixed window (“100 per minute, reset on the minute”) allows a nasty double-burst: 100 at 11:00:59 and 100 at 11:01:00 = 200 in one second. A sliding window counts the last 60 seconds continuously, smoothing that boundary. Token bucket already avoids this — which is why it's the usual default.

4Distributed & atomic (Redis + Lua)

Because many workers share one limit, the counter must live in a shared store (Redis). And “read count → check → increment” must be atomic, or two workers both read “99,” both proceed, and you exceed the limit — a classic race. A Lua script runs the check-and-decrement as one indivisible operation on Redis.

🛣️ Analogy — a highway toll boothCars pass at a steady metered rate; a few can go through quickly if a gap built up (burst up to capacity), but the booth never lets a flood onto the road at once.
⚠️ The race you must preventWithout atomicity, N workers reading the counter simultaneously all think there's room and all proceed → you blow the limit. The Lua script (or an atomic Redis command) makes the check-and-take one step. This is the “distributed rate limiting” interview point.
🔗 Ties back to L1Waiting for a token must be await asyncio.sleep(...), never a blocking sleep — or you'd freeze the event loop while “rate limiting,” starving every other request.
📝 Cheat-sheet
  • Token bucket: refill rate = sustained rate; capacity = burst size.
  • Fixed windows allow a 2× boundary burst; sliding windows / token bucket smooth it.
  • Counter lives in Redis (shared across the fleet).
  • Check-and-take must be atomic (Lua) to avoid races.
  • Wait for tokens with a non-blocking sleep.

stop hammering a failing provider

1The problem: piling onto a sick dependency

When a provider starts failing or hanging, naïvely retrying makes it worse — you add load to something already struggling, tie up your own workers waiting on timeouts, and the failure cascades back into your system. The breaker's job: notice the trouble and stop calling for a while, so both sides can recover.

2The three states

3Why “fail fast” helps everyone

In the OPEN state you return an error instantly instead of waiting on a doomed call. That frees your workers (no piling up on timeouts), removes load from the struggling provider so it can recover, and lets your fallback (4·5) kick in immediately. Half-open is the careful “is it back yet?” probe — you risk one or two calls, not a flood.

⚡ Analogy — an electrical fuseA fuse trips to stop a fire (OPEN). You don't just keep shoving power into a fault — you wait, then test the wire once (half-open) before restoring full power (CLOSED).
⚠️ Tuning is the hard partToo sensitive → it flaps open/closed on normal blips. Too loose → it lets failures through too long. Tune the failure threshold, the rolling window, and the cooldown to the provider's real behavior — and use a rate (e.g. >50% of the last 20 calls) rather than a raw count.

📝 Cheat-sheet
  • States: CLOSED (normal), OPEN (fail fast), HALF-OPEN (probe).
  • Trip on a failure rate over a rolling window, not a raw count.
  • OPEN frees your workers + lets the provider recover.
  • Half-open risks a few probes to test recovery.
  • Retry = single blip; breaker = sustained outage; they compose.

Retry + Backoff + Jitter

recover blips without a stampede

1Only retry the right things

Retry transient failures (a timeout, a 503, a dropped connection) — not permanent ones (a 400 bad request, a 401 auth error): retrying those just wastes calls. And only retry operations that are safe to repeat (idempotent) — which is exactly why you built idempotency keys in S0·3.

2Exponential backoff — wait longer each time

Don't retry instantly and repeatedly — that hammers a recovering service. Wait an exponentially growing delay: ~1s, 2s, 4s, 8s… giving the dependency room to recover, and capping total attempts so you don't retry forever.

3Jitter — the part everyone forgets

If 500 workers all fail at the same instant and all back off by exactly 1s, 2s, 4s… they retry in perfect sync — a “thundering herd” that spikes the provider the moment it recovers and knocks it down again. Jitter adds randomness to each delay so retries spread out instead of clumping.

📞 Analogy — a busy phone lineIf the line's busy you wait longer each redial (backoff). But if everyone redials at the exact same second, the line jams forever — so you each wait a slightly random amount (jitter) and get through.
⚠️ Retries amplify loadEach retry multiplies traffic to a struggling service. Combine with a retry budget (cap the % of traffic that is retries) and the circuit breaker (don't retry when it's OPEN) — otherwise your “recovery” logic becomes the outage.
🔗 Ties to S0·3 & S1·5Safe retries require idempotency. This is the same “retries are everywhere → make repeats harmless” thread running through the whole platform.
📝 Cheat-sheet
  • Retry only transient + idempotent operations.
  • Exponential backoff: delay doubles each attempt, with a cap.
  • Jitter = randomness → prevents the thundering herd.
  • Use a retry budget; don't retry when the breaker is OPEN.
  • Naïve retries can turn a blip into an outage.

Fallback Chain

degrade gracefully — carefully

1Keep serving when the primary fails

A fallback chain is an ordered list of alternatives: if the primary provider fails (or its breaker is OPEN), try the next, then the next — so the user still gets an answer instead of an error. It's the “still eat something” safety net.

2Why fallback is a double-edged sword

Amazon's Builders' Library literally has an article titled “Avoiding fallback,” and it's worth internalizing. Fallbacks are dangerous because: (1) the fallback path is rarely exercised, so it's often the least-tested code and breaks exactly when you need it; (2) failures are often correlated — if the primary is down due to a regional outage, the backup may be too; and (3) shifting all traffic to the backup can overload it (it wasn't provisioned for 100%), turning one outage into two.

🍽️ Analogy — a restaurant listYour favorite is full, so you try the next on your list. You still eat — but if you never notice your favorite keeps being full, you miss a real problem; and if everyone in town has the same backup list, that backup is now slammed too.
⚠️ Use deliberately, and alertFallback that fires silently hides the real failure. Always emit a metric/alert when a fallback triggers, make sure the backup has capacity for the shifted load, and test the fallback path regularly (chaos, Stage 12) so it works when it matters.
🔗 Composes with 4·1 & 4·3The “next provider” often is the selector (4·1) picking another healthy candidate; the breaker (4·3) is what says “skip the primary, it's OPEN.” Fallback is the policy that ties them together.
📝 Cheat-sheet
  • Ordered alternatives; serve the first success.
  • Risk 1: fallback path is under-tested (breaks when needed).
  • Risk 2: correlated failures (backup down too).
  • Risk 3: capacity — shifting 100% can overload the backup.
  • Always alert when a fallback fires; test it regularly.

Load Shedding vs Backpressure

survive overload without collapsing

1Why overload causes collapse, not just slowdown

Past a certain load, systems don't just get slower — goodput (useful work completed) actually drops. Queues grow, latency explodes, timeouts fire, clients retry (adding more load), memory balloons — a death spiral. The fix is to deliberately do less so the system stays alive for most users.

2Two responses — from different ends

Shedding is what a server does to protect itself from clients it can't control. Backpressure works when you own both ends (e.g. the gateway → worker pipeline): a full, bounded queue naturally slows the producer.

🚪 Analogy — a nightclubShedding = the bouncer turns people away when it's full (protect the room). Backpressure = a slow-moving queue outside that paces arrivals so the room never overfills in the first place.
⚠️ Shed the right thingsNot all requests are equal. Shed low-priority/background work before paying-customer requests; never shed liveness/health probes (or the orchestrator will kill a pod that was actually fine). Prioritization is what makes shedding graceful instead of random.
🔗 Ties to your SRE worldThis is the same instinct behind Envoy's overload manager and pod resource limits you already operate — now you're implementing the policy, not just configuring it.
📝 Cheat-sheet
  • Overload collapses goodput — do less to stay alive.
  • Shedding = reject excess now (server-side, clients you don't control).
  • Backpressure = slow the source (when you own both ends; bounded queues).
  • Shed by priority; never shed health checks.
  • Partial service > total collapse.

Bulkhead

contain failure to one compartment

1The noisy-neighbor problem

If all your calls share one pool of resources (threads, connections, concurrency slots), a single slow dependency can grab and hold all of them while its calls hang — starving everything else. One sick provider takes down features that had nothing to do with it.

2Isolate resources per dependency

Give each dependency its own bounded pool (a connection pool, or a concurrency limit / semaphore). Now if provider A hangs, it can only exhaust A's pool — calls to B and C keep flowing. You've drawn watertight compartments.

3Sizing & the resilience trio

Size each pool for its dependency's normal concurrency plus headroom — too small throttles healthy traffic, too big defeats the isolation. Bulkheads rarely work alone: pair with a timeout (so a hung call releases its slot) and a circuit breaker (so you stop filling a doomed pool at all).

🚢 Analogy — a ship's watertight compartmentsIf one compartment floods, the bulkheads keep the water contained so the whole vessel doesn't sink. Each dependency gets its own sealed compartment.
💡 The resilience trioTimeout + Bulkhead + Circuit Breaker are the classic combination: the timeout frees a stuck resource, the bulkhead limits how many can get stuck, and the breaker stops sending work into the failure. Together they turn “one dependency down” into “one feature degraded.”
🔗 Where it livesIn Nataraja, each LLM provider gets its own concurrency limit + connection pool — so a hung provider can't consume the workers that should be serving the healthy ones.
📝 Cheat-sheet
  • Separate resource pools per dependency (connections / concurrency).
  • One dependency's failure can't exhaust shared resources.
  • Size for normal concurrency + headroom.
  • Always pair with timeouts + circuit breakers (the trio).
  • Turns “dependency down” into “one feature degraded.”

Topics, Partitions & Offsets

how Kafka organizes events

1Kafka is a durable, append-only log

Kafka isn't a queue that deletes messages when read — it's a durable log. Events are appended to topics and kept for a retention period, so many independent consumers can read the same stream, and you can replay history.

2Partitions = parallelism + ordering

Each topic is split into partitions. Partitions are the unit of parallelism (more partitions = more consumers can work in parallel) and the unit of ordering: messages are ordered within a partition, but not across partitions.

3Offsets and the partition key

Every message has an offset — its position in the partition — which consumers use as a bookmark to track progress and to replay from any point. Which partition a message lands in is decided by the partition key (e.g. job_id): same key → same partition → guaranteed order for that job.

📚 Analogy — library shelves & slot numbersShelves = topics, split into sections = partitions; each book has a slot number = offset. You always know where you are and can go back to any slot.
💡 The partition key is a design decisionKey by job_id and all of a job's events stay ordered on one partition. A bad key (e.g. everything to one partition) destroys parallelism or creates a hot partition.
🔗 Sets up consumer groups (5·2)Partitions are what a consumer group divides among its members — the basis of scaling workers.
📝 Cheat-sheet
  • Kafka = durable, replayable append-only log (not delete-on-read).
  • Partition = unit of parallelism AND ordering.
  • Order guaranteed within a partition, not across.
  • Offset = bookmark → track progress & replay.
  • Partition key (e.g. job_id) decides ordering & balance.

Consumer Groups

scale workers, keep order

1Share a topic's partitions across a team

A consumer group is a set of consumers that split a topic's partitions among themselves, so each message is processed once per group. Add consumers to the group to process more in parallel.

2One partition → one consumer (the cap)

Within a group, each partition is read by exactly one consumer. So your maximum parallelism equals the number of partitions — 4 partitions can be shared by at most 4 active consumers; a 5th sits idle. You size partitions for future scale.

3Rebalancing when membership changes

When a consumer joins or dies, the group rebalances — partitions are reassigned. Rebalancing briefly pauses consumption, so you want it to be rare and fast; sticky assignment strategies minimize churn.

👥 Analogy — a team sharing one pileEach task is handled by exactly one teammate; add teammates to clear the pile faster — but you can't have more active workers than there are stacks (partitions).
💡 Multiple groups read independentlyDifferent consumer groups each get the full stream — so your worker group and your analytics group can both consume the same topic at their own offsets.
⚠️ Rebalances pause workFrequent joins/leaves cause repeated rebalances (stop-the-world pauses). Keep consumers stable; use cooperative/sticky rebalancing.
📝 Cheat-sheet
  • Group splits partitions → each message processed once per group.
  • One partition → one consumer in the group.
  • Max parallelism = number of partitions.
  • Different groups each read the whole stream independently.
  • Rebalances (on join/leave) briefly pause consumption.

Delivery & the Exactly-Once Myth

effectively-once, not magic

1At-least-once is the default

By default Kafka gives at-least-once: a consumer may process a message, crash before committing its offset, and get it again on restart. Duplicates are normal — the same reality you met in S1·5, now at the backbone level.

2How offsets create duplicates

The offset is your “I've read up to here” bookmark. If you commit the offset after processing (correct) but crash in between, the message is re-read. If you commit before processing, a crash loses it. Offset-commit timing is the whole game.

3Reaching effectively-once

True exactly-once delivery is impossible over a network. You reach effectively-once by combining at-least-once delivery with idempotent processing (dedup by key) — or, within Kafka-to-Kafka flows, its transactional producer that ties writes and offset commits into one atomic step.

✉️ Analogy — a letter delivered twiceYou can't guarantee both “always delivered” and “never twice,” so you make opening it twice harmless instead of praying the post is perfect.
⚠️ Don't chase exactly-once deliveryIt doesn't exist across systems. Design idempotent consumers and commit offsets after success — that's the honest, robust answer.
🔗 Same principle as S1·5Idempotent consumers keyed by a stable id turn duplicates into no-ops — the thread running through the whole platform.
📝 Cheat-sheet
  • Default = at-least-once → expect duplicates.
  • Commit offsets AFTER processing (before = data loss).
  • Exactly-once delivery is impossible across systems.
  • Effectively-once = at-least-once + idempotency.
  • Kafka transactions give exactly-once within Kafka-to-Kafka.

Schema Registry & Evolution

Producers and consumers must agree on message shape. A schema registry stores versioned schemas and checks that every new version is compatible — so formats can change over time without breaking anyone.

2Compatibility modes

You pick a rule: backward (new consumers can read old data), forward (old consumers can read new data), or full (both). This decides which changes are allowed and in what order you deploy producers vs consumers.

📄 Analogy — a shared, versioned contractBoth offices agree on a form. You can add an optional box, but you can't rip out a box the other side depends on without a new agreed version.

Outbox Pattern

no lost or duplicated events

1The dual-write problem

You often need to do two things: update the database and publish an event. Do them as two separate writes and a crash between them leaves you inconsistent — DB updated but no event, or event sent but DB rolled back. There's no transaction spanning both systems.

2Write the event intent atomically

The outbox pattern writes the business change and an outbox row (the event to publish) in the same database transaction. They commit together or not at all — so the DB and the “to-publish” list can never disagree.

3The relay (and idempotency)

A separate relay process reads unsent outbox rows and publishes them to Kafka, then marks them sent. If the relay crashes after publishing but before marking, it republishes — which is fine because consumers are idempotent (5·3).

🖋️ Analogy — one pen strokeYou write the diary entry and the “to-mail” note in the same stroke — the record and the intent to notify are created together, atomically.
💡 Turns a distributed problem into a local oneThe only atomic thing you needed was a single-DB transaction — which you already have. The relay handles the rest, idempotently.
🔗 CDC is an alternative (5·9)Instead of a relay reading an outbox table, CDC can stream the outbox (or the change itself) straight from the DB log.
📝 Cheat-sheet
  • Dual-write (DB + publish separately) can go inconsistent on crash.
  • Outbox: business change + outbox row in ONE txn.
  • A relay publishes outbox rows to Kafka, then marks sent.
  • Republish-on-crash is safe because consumers are idempotent.

Dead-Letter Queue (DLQ)

quarantine poison messages

1Poison messages block the line

Some messages fail no matter how many times you retry — malformed data, a bug, a permanently missing dependency. If you keep retrying one at the head of a partition, it blocks everything behind it. That's a poison message.

2Move it aside after N attempts

A dead-letter queue is a side topic. After a message fails a set number of times, you move it to the DLQ and advance past it, so the main pipeline keeps flowing. The failure is preserved, not lost.

3The DLQ is a workflow, not a graveyard

A DLQ only helps if you watch it: alert on new entries, inspect why they failed, fix the cause, and replay them back into the pipeline. An ignored DLQ is just silent data loss with extra steps.

🔗 Pairs with retries (S4·4)Retry transient failures a few times first; only truly stuck messages go to the DLQ — retry then quarantine.
📝 Cheat-sheet
  • Poison message = fails forever, blocks the partition.
  • DLQ = side topic for repeatedly-failing messages.
  • Move after N attempts; keep the main stream flowing.
  • Alert, inspect, fix, and REPLAY from the DLQ.
  • An ignored DLQ is silent data loss.

CQRS

separate writes from reads

1One model can't be great at both

A data model optimized for writing (normalized, event-based, consistent) is often bad for reading (needs joins, slow queries). CQRS — Command-Query Responsibility Segregation — splits them: a clean write model, and one or more read models shaped for queries.

2Read models are projections

Read models are built by projecting the event stream (5·1) into query-optimized shapes — a table per dashboard, a denormalized view, a search index. Because they're derived, you can add new read models anytime and rebuild them by replaying events.

3Eventual consistency

The read model updates shortly after the write, not instantly — so a query right after a command may briefly show stale data. You design the UX around this eventual consistency (e.g. optimistic UI, “processing…” states).

🗄️ Analogy — writing desk & reading libraryA desk for recording changes cleanly, and a library organized for fast lookup — each shaped for its own job.
💡 Read models are disposableSince they're just projections of events, you can drop and rebuild them, or add a new one for a new feature, without touching the write side.
⚠️ Eventual-consistency lagReads can trail writes by moments. Never assume a read immediately reflects the write that just happened.
📝 Cheat-sheet
  • Split write model (events) from read model(s).
  • Read models = projections of the event stream.
  • Add/rebuild read models freely by replaying events.
  • Reads are fast & query-shaped; writes stay clean.
  • Trade-off: eventual consistency (read lags write).

Saga

multi-step transactions without a global lock

1You can't hold one transaction across services

A workflow that spans several services (reserve credits → run job → charge) can't be wrapped in one ACID transaction — there's no lock across systems. A saga coordinates it as a series of local transactions with compensations to undo on failure.

2Compensating actions

Each step has a compensating action that undoes its effect (un-reserve the credits, refund the charge). If a later step fails, you run the compensations for the completed steps in reverse — a business-level rollback, since a technical rollback isn't possible.

3Orchestration vs choreography

Orchestration: a central coordinator tells each service what to do and triggers compensations (explicit, easier to reason about). Choreography: services react to each other's events with no central brain (decoupled, but harder to follow). Pick per complexity.

🧳 Analogy — a group bookingIf the hotel step fails, you auto-cancel the flight you already booked — undoing earlier commitments cleanly, one by one.
💡 Compensations must be idempotent tooA compensation might run more than once (retries). “Refund” must be safe to attempt twice — same idempotency discipline everywhere.
⚠️ Compensations can failWhat if the refund itself fails? Real sagas need retries, alerting, and sometimes manual intervention for stuck compensations.
📝 Cheat-sheet
  • Coordinates multi-step distributed work (no global ACID).
  • Each step has a compensating action to undo it.
  • On failure, compensate completed steps in reverse.
  • Orchestration (coordinator) vs choreography (events).
  • Compensations must be idempotent & can themselves fail.

Multi-Tenancy & Isolation

1Shared infrastructure, private data

OAuth2 / OIDC / JWT

standard authentication & authorization

1Two different questions: authN vs authZ

Authentication (authN) = who are you? Authorization (authZ) = what may you do? OAuth2 handles delegated authorization; OIDC adds an identity layer on top (authN); a JWT is the signed token that carries both.

2The flow

The user authenticates with the Identity Provider (Keycloak). The IdP issues a signed JWT containing identity + scopes. The client sends that token with each request, and every service verifies the signature and checks the scopes — no round-trip to the IdP per call.

3What a JWT is (and its trade-off)

A JWT is header.payload.signature. Any service can verify the signature with the IdP's public key and trust the claims — stateless, no DB lookup. The trade-off: a JWT is valid until it expires, so revocation is hard. You use short lifetimes + refresh tokens to limit exposure.

🎪 Analogy — a festival wristbandVerified once at the entrance (login), then just flashed at each stage (services verify the signature) — no re-checking your ID everywhere.
⚠️ A JWT is signed, not encryptedIts payload is readable by anyone who has the token (base64, not secret). Never put passwords or secrets in it — only identity + claims.
💡 Stateless verification vs revocationNo DB hit to verify = fast & scalable, but you can't instantly kill a token. Keep lifetimes short (minutes) and rotate via refresh tokens.
📝 Cheat-sheet
  • authN = who you are; authZ = what you may do.
  • OIDC = identity on top of OAuth2; JWT carries both.
  • JWT = header.payload.signature; verify signature locally.
  • Stateless (no DB lookup) — but revocation is hard.
  • Short lifetimes + refresh tokens; never put secrets in a JWT.

Encryption in Transit & at Rest

protect data moving and stored

1Two threats, two defenses

Data faces two risks: being intercepted as it travels the network, and being read from a stolen disk or backup. You defend both: encrypt in transit (TLS) and at rest (KMS-managed keys).

2In transit: TLS everywhere

3At rest: envelope encryption

Encrypting big data directly with a master key is slow and risky. Envelope encryption generates a per-object data key to encrypt the data, then encrypts that data key with a master key in KMS. To rotate, you re-encrypt the small data keys, not the terabytes.

⚠️ Key management is the hard partEncryption is easy; safely storing, rotating, and controlling access to keys is the real work — which is why you use a KMS/Vault, not homegrown key handling.
📝 Cheat-sheet

  • At rest: KMS-managed keys on disk/backups/object store.

  • The hard part is key management — use KMS/Vault.
